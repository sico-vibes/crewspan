# Crewspan: the human and agent workspace built on Paperclip

**Version 2 — Multica research edition · 24 September 2026**
**Status:** product and engineering plan, not a claim that the features exist today. This is a standalone successor to Version 1; the original file remains unchanged.

## Research finding and strategic adjustment

Multica is a serious direct comparator. Its documented product already puts humans, agents, projects, work items, shared skills, run histories and notifications in one workspace; it can assign work to a person, agent or squad, and run coding tools on connected computers. Crewspan must not claim that putting humans and agents together, agent access controls, multi-repository projects, or agent teams are novel by themselves. [Multica architecture](https://multica.ai/docs/developers/architecture), [projects](https://multica.ai/docs/projects), [agents](https://multica.ai/docs/agents), [squads](https://multica.ai/docs/squads).

**The sharper Crewspan proposition:** a Paperclip-native operating workspace for *any* knowledge-work team, with a mixed human/agent organisation, company-grade resource permissions, explicit agent allocation and model authority, verified per-run isolation, bounded delegation with human review, and one end-to-end view of accountable work. Multica's public documentation is strongest around AI coding workflows. Its workspace roles primarily govern settings and membership, while project collaboration is broadly open to workspace members; its agent Access is a separate control. Crewspan's fine-grained project, file, conversation, agent, credential and runtime permissions are therefore a deliberate product investment. This comparison describes the documented product, not an exhaustive security audit. [Multica members and roles](https://multica.ai/docs/members-roles), [projects](https://multica.ai/docs/projects), [agents](https://multica.ai/docs/agents).

| Multica finding | Crewspan response | Priority |
|---|---|---|
| Agent identity, execution runtime and individual run are distinct; the server coordinates while connected computers execute. | Model those concepts separately, extending Paperclip's adapters, environments and execution records. Add a remote runner only after auditing what Paperclip already supports. | Foundation |
| An agent can have an owner and an Access list; runtime computers are private to their owner by default. | Keep agent allocation, agent invocation, runtime use and credential use as separate grants. Require the machine owner's consent for a personal runtime. | Foundation |
| A squad has an agent leader, human/agent members and a leader wake-up cycle. | Permit either a human or agent team lead; make child work a typed task/dispatch record with reviewer, evidence, budget and loop guards. | Core |
| Assignment can set ownership without starting execution; mentions can request a single run. | Expose **Assign** and **Start run** as separate decisions everywhere, with a preview of what a mention will trigger. | Core |
| Linked local directories support Direct and Parallel worktree modes, with capability checks at save and run time. | Offer clear execution modes, recorded input snapshots and fail-closed capability checks. A worktree is never presented as a security sandbox. | Core |
| Workspace skills and scheduled/webhook Autopilots make methods and recurring work reusable. | Extend Paperclip's existing skill and routine mechanisms; add scoped versioning, review, visible effective skills and policy-checked automation. | Core |
| Its security documentation says default runs inherit the daemon user's filesystem, credentials and network reach. | Make tested per-run containment a release gate; show any compatibility override plainly. | Differentiator |

## 1. Product contract and foundation

**Crewspan is a public, self-hosted fork of Paperclip for knowledge-work organisations.** People and AI agents share an organisation, projects, work, files and conversations. An owner can appoint a human or AI CEO, build mixed reporting lines beneath them, allocate agents to specific people or teams, and govern what those agents may see, use and spend. Every delegated task remains visible from assignment through execution, review and accepted result.

A complete first public release must support the whole core journey: **set up an organisation → invite people → appoint leadership → create projects and shared resources → allocate agents → communicate → delegate work → review results → inspect cost and activity**. Engineering can deliver this in milestones, but the public release gate covers the complete journey.

### Fork baseline and boundaries

- Fork the latest verified stable Paperclip release at implementation start; the current researched stable baseline is `v2026.916.1`. Keep the upstream Git remote and document the pinned commit. Preserve Paperclip’s MIT notice and attribution. [Paperclip releases](https://github.com/paperclipai/paperclip/releases), [license](https://github.com/paperclipai/paperclip/blob/master/LICENSE).
- Retain Paperclip’s React UI, Express API, PostgreSQL/Drizzle data layer, Better Auth, adapters, project workspaces, tasks, approvals, run history, budgets, Connections and artifacts. Its existing monorepo is the implementation home; Crewspan should not become a separate frontend placed over Paperclip. [Architecture](https://github.com/paperclipai/paperclip/blob/master/docs/start/architecture.md).
- Draw product inspiration from Buzz’s DMs, channels and shared human/agent presence, elnagdy’s bounded delegation and review loop, 9Router/OmniRoute’s quota-aware routing, and Multica's execution and collaboration patterns. Implement these as Crewspan features or optional connections; do not merge their applications into the fork. [Buzz](https://github.com/block/buzz), [delegate-skills](https://github.com/amElnagdy/delegate-skills), [9Router](https://github.com/decolua/9router), [OmniRoute](https://github.com/diegosouzapw/OmniRoute).
- Maintain a **Paperclip compatibility map** for every existing surface: inherited unchanged, extended, or deliberately replaced. New work must preserve existing API behaviour and migrate existing Paperclip data unless a documented compatibility test proves that impossible.
- Use **Crewspan** as the project codename. Treat public branding, domain and trademark clearance as a separate release decision; no visual rebrand is required to develop the product.

### Success criteria

A pilot organisation with at least two humans, two agents and two projects must be able to prove that:

1. A human CEO and an AI CEO are both valid appointment choices, and mixed reporting lines work.
2. A project member can operate only allocated agents and see only authorised projects, files, conversations, runs and costs.
3. An agent assigned to Project A cannot read Project B’s repository, files, credentials or API data.
4. A channel mention can create governed agent work; a reviewer can inspect its evidence, request changes and accept the outcome.
5. The owner can see the complete work and spend trail without searching through raw transcripts.
6. The UI remains recognisably Paperclip in its layout, components, terminology, states and density.
7. A person can assign ownership without starting a run; a mention or automation shows the target, context, runtime and expected budget before it starts.
8. A mixed team can delegate work through accountable child tasks, recover after a runner disconnects, and reach a human sign-off without duplicated runs.
9. A project can link several repositories or non-code resources while its runner cannot reach an unrelated project on the same VPS.

## 2. Organisation, authority and access

### Separate four relationships

Crewspan must model these independently throughout the database, API and UI:

| Relationship | Meaning |
|---|---|
| **Reporting** | Who manages whom in the organisation chart. |
| **Work ownership** | Who is accountable for a task and its final decision. |
| **Access and authority** | What a person or agent may view, assign, invoke, approve or configure. |
| **Execution policy** | Where an agent runs and which data, tools, credentials, provider, model, effort and budget it may use. |

A reporting line never grants access by itself. A project membership never grants model or credential access by itself. **Agent ownership, agent invocation, runtime ownership and runtime use are four more separate facts**: an authorised person may operate an agent only when all relevant grants intersect. Agent availability (online/eligible) and workload (queued/running) are distinct from permission. Multica's agent and runtime documentation makes this separation explicit; Crewspan applies it throughout the Paperclip fork. [Agents](https://multica.ai/docs/agents), [daemon and runtimes](https://multica.ai/docs/daemon-runtimes).

### Hybrid organisation

- Extend the existing agent tree with typed **human and agent organisation nodes**. Each node has a title, team, capabilities, status and optional manager. Enforce one direct manager per node, no reporting cycles and one active CEO appointment per organisation. The owner’s Board role sits above this tree as governance authority.
- Let the Board appoint a human or agent CEO and reassign that appointment through an audited transition. Human leaders and AI leaders can manage mixed teams. Preserve existing agent identities, reporting data and task history during migration.
- Keep job position separate from permission role: “CEO” or “Research Lead” describes organisational responsibility; owner, administrator, manager, member and viewer templates describe default powers.
- Add a human project lead alongside Paperclip’s agent project lead. A project can have one accountable lead and additional contributors. Existing human task assignees continue to work.
- Add **agent allocation**: an agent may be assigned to a human steward, team or approved shared pool. Allocation states who may discover, chat with and request work from that agent; explicit action grants determine what they can actually do. An owner can grant additional operators without moving the agent in the chart.

Paperclip has human members and task assignees, but its documented model does not yet make humans full organisation nodes or give a member access only to selected agents. Its existing project/agent membership rows mainly control sidebar visibility. Crewspan must implement actual server-enforced resource access. [Hybrid-human feature request](https://github.com/paperclipai/paperclip/issues/11353), [membership contract](https://github.com/paperclipai/paperclip/blob/master/doc/SPEC-implementation.md).

### Permission system

- Use one central authorisation service for users and agents. A decision evaluates **principal + action + resource + organisation + current grants** and returns an allow/deny result with an auditable reason.
- Resource scopes are organisation, project, folder, document, asset, task, conversation, agent, run and connection. Grants can target a person, agent or team. New organisations start with **default-deny project access**; owners retain audited administrative authority.
- Project grants may flow to child tasks and folders. Marking a folder, task or channel “restricted” breaks that inheritance and requires explicit membership. Revocation applies to new API reads, downloads, subscriptions, tool calls and runs immediately; active agent runs holding revoked data are cancelled.
- Define separate actions for viewing an agent, messaging it, assigning it work, invoking it, reviewing its work, changing its configuration, granting its credentials and changing its budget. Define runtime registration, inspection, sharing, assignment and execution separately as well. An administrator's ability to maintain a runtime record does not imply consent to spend a person's computer or tool account. A manager can allocate inside an envelope set by the owner but cannot expand that envelope.
- Apply the same check to list and detail endpoints, search, autocomplete, notification payloads, WebSocket events, file previews/downloads, exports, MCP/tool access and agent context retrieval. Hidden data must not leak through counts, titles or “permission denied” details.
- Keep an immutable audit record for grants, denials on sensitive actions, configuration changes, approvals, credential use, task dispatch and owner override.
- Enforce authorisation when a task is drafted, when a run is queued, when a runner claims it, and when tools request resources. A grant revoked while work is queued or active must block the claim or stop the run. Use scoped, short-lived per-run credentials that identify the agent and run; strip them from unrelated child processes, logs and artifacts. Re-check permissions at every API/tool call rather than trusting a prompt or the initial queue decision. [Multica execution path](https://multica.ai/docs/developers/architecture), [runtime token behaviour](https://multica.ai/docs/daemon-runtimes).

### Access requests and approvals

- A person can request access to a project, folder, agent, runtime, provider/model, connection or higher budget from the point where they encounter the restriction. The request records the requested scope, reason, duration and approving authority.
- Route requests to the project lead or authorised manager when inside their envelope; route any expansion of organisation policy, credentials or spend ceiling to an owner or designated Board approver.
- Approval creates a scoped grant with optional expiry; rejection includes a reason. Revocation invalidates it without deleting the request history. Agents may propose requests but cannot approve their own expansion.
- Provide one review surface that shows **what will become visible or executable** before approval. Avoid a generic “approve access” button with unclear consequences.

## 3. Shared work, delegation and communication

### Projects, files and knowledge

- Preserve Paperclip projects, tasks, repositories, execution workspaces, issue documents, attachments and the company Artifacts view. A project may be created without a repository; this is essential for research, operations, design and other knowledge work. Repository-backed projects may select multiple repos. [Project workspaces](https://github.com/paperclipai/paperclip/blob/master/skills/paperclip/references/api-reference.md), [issue documents](https://github.com/paperclipai/paperclip/blob/master/docs/api/issues.md), [Artifacts](https://github.com/paperclipai/paperclip/blob/master/releases/v2026.609.0.md).
- Add a **project Files area** using Paperclip’s existing attachment and artifact storage: folders, uploaded assets, editable documents, versions, previews, ownership, links to tasks and project-level search. Keep an “organisation shared” area for templates and approved common knowledge.
- Distinguish three file types visibly: **managed files** stored by Crewspan, **repository files** belonging to a source repo, and **execution files** produced inside a run workspace. A result intended for review must be published as a managed artifact or explicit versioned document; a local path alone does not count as delivery.
- Before any document, file, transcript or search result reaches an agent, enforce the agent’s resource grant and the initiating human’s rights. Do not inject organisation-wide context containing restricted material into every agent; assemble layered organisation, team, project and task context only from material in the effective access intersection. Assemble context from the task brief, explicitly attached resources and permitted retrieval results; record source links. A folder assignment defines available material, not automatic inclusion of all its contents in a model context window.
- For each project resource, store its kind, owning project, allowed runtime pool, checkout/ref or managed-file version, write mode and retention. Show the exact input revision or file versions on the run. If a local directory is linked, canonicalise and revalidate its path and symlinks, refuse system/home/root locations, and bind it to the approved machine. Multiple linked repositories must each pass the same access and containment checks. [Multica project resources](https://multica.ai/docs/project-resources).
- Keep uploads and downloads scoped to the authorising resource. Validate type and size, scan uploaded files, sanitise previews, issue short-lived download access, and exclude revoked material from search results and cached context.

### Agent, runtime and run contracts

- **Agent** is the persistent worker identity: role, instructions, skills, allocation, model envelope, approved tools and history. **Runtime** is a particular execution environment: runner owner, machine/pool, installed adapter or tool, capabilities, online state, capacity and isolation grade. **Run** is one durable invocation of an agent on an approved runtime with an effective policy snapshot, task context, temporary credentials, usage and output. Keep these records independent so moving an agent does not rewrite history. [Multica architecture](https://multica.ai/docs/developers/architecture).
- Start with a company-owned runner pool on the VPS. Support opt-in remote or personal runners later through a runner protocol built on Paperclip execution abstractions: authenticated registration, explicit capability report, heartbeats, lease/claim, cancellation, progress stream, result upload and disconnected recovery. Personal computers and local subscriptions stay private by default; only the owner can share that capacity. A run is pinned to an approved runtime unless a new, visible rescheduling decision proves equivalent policy, context and cost.
- Resolve dispatch from **requester × agent allocation × project/resource access × provider/model policy × runtime consent/capabilities × budget × isolation grade**. Display the effective combination before execution. Queue with a durable idempotency key and capacity limits per runner, agent, project and provider account. Offline runners show a waiting state and do not silently shift to another computer or unsandboxed mode.
- The control plane owns durable state in PostgreSQL. A live event wakes the runner and updates the browser, while polling/requery after reconnect closes gaps. Use one claim transaction to prevent two runners from taking the same run. Temporary credentials are scoped to the run and expire on completion/cancellation. A lost heartbeat triggers a bounded recovery policy; a resumed run keeps its original identity and cost trail. [Multica execution path](https://multica.ai/docs/developers/architecture), [daemon dispatch](https://multica.ai/docs/daemon-runtimes).

### Agent runtime and delegation

- Use Paperclip’s existing task/run/approval system as the record of work. A **delegation** is a parent task linked to one or more bounded child tasks, each with a brief, permitted inputs, chosen agent or lane, run policy, expected deliverable, reviewer and acceptance criteria.
- The visible lifecycle is **draft → assigned → authorised → queued → running → result submitted → review → accepted / changes requested / cancelled**. Assignment alone records ownership; **Start run** is a separate operation. A one-off mention can invoke an agent without changing task ownership. Task status and run status remain distinct: a finished run does not automatically mean the task is accepted. [Multica assignment flow](https://multica.ai/docs/assigning-issues). Each stage has an accountable owner and a durable event. A failed or interrupted run resumes or retries according to an explicit policy; it does not silently create a second task or duplicate a charge.
- Support delegation lanes such as research, writing, coding and review. A lane specifies an eligible agent class and an approved model/effort envelope. A human or coordinating agent may choose a lane, but dispatch resolves to a particular authorised agent and records the effective configuration.
- A **delivery team** has a human or AI lead and a roster of human and agent members with role descriptions. The lead receives a parent task, selects one or more authorised members, creates typed child assignments, waits for their results, requests independent review where specified, and brings the parent to human sign-off. The lead's own coordination turn stops after dispatch; member updates can reawaken it, subject to event deduplication, depth limits, loop detection and per-task run caps. Team membership never bypasses access grants. This extends Multica's agent-led squads with human leadership and explicit child work records. [Multica squads](https://multica.ai/docs/squads).
- The parent task receives a concise child result, linked artifact and verification evidence. Reviewers can open the full run history when needed. The originating agent may continue only after the child result or human decision is recorded.
- Measure **total cost per accepted task**, including parent orchestration, delegates, retries and review. Show estimated versus actual spend and time, but never promise that delegation inherently saves tokens.
- Retain Paperclip Connections as the source of provider credentials. Add a model policy resolver that intersects organisation, project, agent, requester and credential grants before dispatch. Provider fallback stays within that intersection; if no route is authorised, the task pauses with an actionable request. Allow an external OpenAI-compatible router such as 9Router or OmniRoute as an optional endpoint, while Crewspan remains the authority for policy and accounting. Paperclip’s current Connections already distinguish credential ownership and grants from model selection. [Connections release](https://github.com/paperclipai/paperclip/releases/tag/v2026.916.0).

### Execution isolation

- Treat a project working directory as a starting location. It is **not** a security boundary. Use Paperclip’s execution-workspace and environment abstractions, but make a verified isolated runner mandatory for ordinary Crewspan agent execution. [Execution workspaces](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/execution-workspaces-and-runtime-services.md), [filesystem scope](https://github.com/paperclipai/paperclip/blob/master/doc/spec/agent-runs.md).
- On a single VPS, run the control plane separately from agent execution. Provision a per-run or explicitly reusable isolated environment containing only the selected project checkout, approved read-only shared references and scoped credentials. Run as a non-root user, without the host’s home directory, SSH keys, database credentials or container-control socket. Restrict egress to required provider, Crewspan and authorised tool endpoints.
- Expose **Direct** (serial work in an existing directory) and **Parallel** (dedicated worktree/branch) as explicit project resource modes. Default to Parallel for ordinary Git work and avoid Direct on shared VPS repositories except an owner-approved compatibility case. Check runner capability when saving the resource and again when claiming each run. If Parallel cannot be honoured, fail closed and tell the user; never quietly edit the original checkout. Record the base commit and whether approved uncommitted/untracked input was copied. If that snapshot cannot be reproduced within declared limits, stop before execution. Retain failed worktrees and report their paths for recovery. [Multica project resources](https://multica.ai/docs/project-resources).
- Use a separate Git worktree for parallel writable work. Treat the worktree as edit isolation and the runner as access isolation. For non-code projects, provision an empty working area plus selected managed files.
- Disable unsandboxed local adapters for normal users. Provide an owner-only, clearly labelled compatibility override with audit logging for installations that cannot support isolation. A sandbox launch failure fails the run closed.
- Publish a clear threat model: working directory, worktree, agent instructions, tool approval mode and short-lived API tokens are useful, but none alone confines filesystem/network access. Multica's own security documentation states that its default local runs inherit the daemon user's OS permissions; Crewspan's differentiated promise requires a real outer boundary, tested per deployment. [Multica security model](https://multica.ai/docs/security-model).
- Validate each supported adapter/environment pair with a real test attempting to read a neighbouring repo, host secret and forbidden network endpoint. Do not mark an agent “isolated” merely because a config field is present; Paperclip’s optional local Bubblewrap scope is off by default and has had reported adapter and host compatibility issues. [Adapter configuration](https://github.com/paperclipai/paperclip/blob/master/packages/adapters/claude-local/src/index.ts), [reported issue](https://github.com/paperclipai/paperclip/issues/11079).

### DMs, channels and inbox

- Add human↔human, human↔agent and authorised agent↔agent DMs; project and team channels; threads; mentions; attachments; and links to tasks, files, decisions and runs. Private channels are visible only to members. Agents join and read channels under the same explicit membership rules as people.
- The composer previews which `@agent` or team mentions will start runs, on which task and with which context, before sending. An `@agent` mention first checks membership, invocation authority, model policy, budget and context scope. If allowed, it creates a task-backed interaction and posts progress/result back to the thread. If denied, show the exact available action, such as “Request access,” without exposing the agent’s private configuration. A normal conversation message never silently authorises deployment, purchase, credential use or another governed action.
- Separate **exploratory private chat** from **accountable task work**. A DM has only the explicitly authorised chat context; it does not silently inherit every project document or create a task. Offer **Turn into task** to capture a message, project, attachments, owner and acceptance criteria. Task and channel discussions retain their task link and audit trail. [Multica agent chat](https://multica.ai/docs/chat).
- Keep a single **actionable Inbox** built from assignments, mentions, review requests, approvals, access requests, agent questions, run failures and budget incidents. Deduplicate by underlying work item and event family, distinguishing unread notification state from unresolved task state; a run failure must still be visible after someone archives its notice. [Multica Inbox](https://multica.ai/docs/inbox). Each item links to its underlying record and has read/archived state; archiving does not resolve the work. Add per-user notification preferences and a daily digest, with in-app live delivery first.
- Preserve Paperclip’s existing task conversations, “Mine” work and experimental agent chat where useful. Unify their navigation and notification presentation rather than creating a second, inconsistent task database. AgentMail and external chat connectors remain optional integrations, not the internal inbox implementation. [Current chat and Connections release](https://github.com/paperclipai/paperclip/releases/tag/v2026.916.0), [Inbox API](https://github.com/paperclipai/paperclip/blob/master/skills/paperclip/references/api-reference.md).

### Reusable skills, routines and controlled learning

- Audit Paperclip's company skill library and routine facilities first. Extend those records rather than creating a second store. A skill has an owner, purpose, `SKILL.md` content, optional support files, version, source/provenance, approval state and bindings to agents or projects. A run records the exact effective skill versions. A restricted project's skill must not be attached to an agent that cannot read that project. Untrusted imported scripts require an explicit review and the same runner containment as any other code. [Multica skills](https://multica.ai/docs/skills).
- Give recurring work a reusable brief or runbook, a schedule or signed webhook trigger, assignee, project/context scope, budget, subscriber list and failure policy. Let an operator choose **Create task** for work that needs collaboration/review or **Run only** for bounded background work. Both modes keep a durable run record and use the same access/model/runtime checks. Webhooks require idempotency keys, payload limits and event filtering. Repeated failures pause the routine and notify an owner. [Multica Autopilots](https://multica.ai/docs/autopilots).
- Add an opt-in improvement loop: after an accepted result, an agent or reviewer may propose a new/updated skill from the task evidence. The proposal is a diff with source links, privacy checks, affected agents and estimated prompt cost. A human steward approves, edits or rejects it; subsequent runs can use the version, historical runs do not change. Measure whether the revised skill improves accepted-task cost/quality. Do **not** describe this as a shipped Multica feature; its current skill docs describe human-managed skills, while an issue proposes closed-loop improvement. [Multica skills](https://multica.ai/docs/skills), [proposal](https://github.com/multica-ai/multica/issues/4433).

## 4. Interface and technical implementation rules

### UI/UX: a strict Paperclip expansion

Paperclip’s `DESIGN.md` is the source of truth for Crewspan interface work. Its stated screen priority is: **what is happening, does it need me, what do I do about it**. Use its existing React components, layouts, status vocabulary and CSS token root; do not start a parallel design system. [Paperclip design principles](https://github.com/paperclipai/paperclip/blob/master/DESIGN.md).

- Preserve the existing dashboard, project, task, agent, run, approval, cost, settings and Artifacts screens as recognisable surfaces. Extend their existing panels and actions. Add only the missing destinations: **People** within the org area, **Chat**, and **Files** within projects; evolve “Mine” into the unified Inbox.
- Reuse existing Button, Card, Badge, Table, form, drawer, status and empty-state components before adding variants. Put any new visual values in Paperclip’s token source, `ui/src/index.css`. Do not hardcode a new palette, type scale, spacing scheme or motion language.
- Make human and agent identity distinct through a consistent avatar/type marker while keeping them equal participants in the same org chart, assignee picker, message composer and activity trail. Show **authorised**, **online/available** and **busy/queued** as separate states; do not collapse them into one green dot. A card should expose role, availability and responsibility first; model and raw runtime details belong in a deeper panel.
- Keep the operator view dense and scannable. A task should show its owner, delegated children, latest result, reviewer, blockers and cost before raw logs. Chat should be pleasant for everyday conversation, but task status and approvals remain visible in the same Paperclip visual vocabulary.
- Add an **effective access** panel to each person, agent and runtime: projects they can see, agents they can invoke, connections/models they can use, budget limits, and who granted each right. Show the same effective policy in the assignment composer before dispatch.
- Use action-specific copy: “Assign to Research Agent,” “Start run,” “Request model access,” “Approve £20 increase.” A dispatch preview shows accountable owner, agent/team, input resources, runtime/isolation mode, model/effort, estimate and reviewer. An assignment change affecting an active run offers a separate **Stop current run** action and states what happens if it is left running. [Multica assignment flow](https://multica.ai/docs/assigning-issues). Keep *task* as the UI term even where inherited API paths still say `issue`. Errors explain the denied action and next step without leaking hidden data.
- Match Paperclip’s responsive browser experience and existing installable-web capabilities. Do not make native desktop or mobile rewrites a release prerequisite. Support keyboard navigation, reduced motion, screen-reader labels, contrast and all loading/empty/error states.
- Establish a visual regression baseline from the pinned Paperclip release. New screens must pass side-by-side review in light/dark themes and desktop/narrow layouts. Reject a Crewspan feature if its component, spacing, status colour or navigation behaviour feels imported from another product. Paperclip explicitly uses Storybook as a verification surface. [Design principles](https://github.com/paperclipai/paperclip/blob/master/DESIGN.md).

### APIs, data and events

Extend the existing REST API and shared types with:

- Typed organisation nodes/reporting edges; project leads and agent allocations.
- Resource grants, effective-permission checks and access-request decisions.
- Folder/document/asset metadata and version records.
- Delegation links, briefs, results, review decisions and cost attribution.
- Conversations, membership, messages, mentions and per-user Inbox entries.
- Model policy and route-decision records.
- Runtime registration, owner/consent, capability and capacity records; run leases, effective-policy snapshots, input revision manifests and short-lived credentials.
- Team rosters, child-dispatch events, trigger deduplication, reviewer gates and skill proposal/version records.
- Routine runbooks, triggers, deliveries, subscriptions and failure pause state.

Keep existing task and agent endpoints compatible. Make `assign`, `start`, `stop`, `retry` and `accept` distinct operations with separate authorisation and idempotency rules. A queued run is claimed transactionally; state transitions reject stale leases. Publish permission-filtered events, and requery the database after reconnect because a WebSocket delivery is a hint, not the source of truth. [Multica architecture](https://multica.ai/docs/developers/architecture). Add dedicated endpoints for access requests, conversations, folders and delegations under company-scoped paths. Every write uses the same authorisation service, records an activity event and emits an authorised live update. Use transactional outbox delivery for notifications so a saved decision cannot vanish if a live event fails.

### Self-hosted deployment and operations

- Ship a documented single-VPS Compose path with the Crewspan web/API service, PostgreSQL and a separate runner service. The company runner should start with no access to the control-plane database, host home directory or unrelated repository mounts. Surface a setup report showing whether filesystem, secret and network isolation probes pass. Support Paperclip’s local-disk storage for small single-host installations and S3-compatible storage for larger deployments. Never put agent runners in the control-plane container with broad access to its database or secret store. [Paperclip Docker guide](https://github.com/paperclipai/paperclip/blob/master/docs/deploy/docker.md), [storage guide](https://github.com/paperclipai/paperclip/blob/master/docs/deploy/storage.md).
- Default to Paperclip’s **authenticated** deployment mode for Crewspan organisations, with HTTPS behind a reverse proxy. Preserve existing provider sign-in/API-key flows and Connections rather than inventing a central model billing service.
- Provide setup checks for database migration, storage, runner isolation, provider credentials, public URL and backup health. Back up the database, uploaded files and secrets key together; document restore and an upgrade rollback path.
- Ship an import/upgrade path for an existing Paperclip installation. Existing company-wide visibility remains readable during migration, but the administrator must review and activate scoped Crewspan policies before inviting restricted users. New Crewspan organisations use the scoped default from creation.
- Explain runtime ownership in deployment docs: a company VPS pool uses organisation credentials and quotas; a connected personal computer uses its owner's tool accounts, directories and explicit sharing choice. A server-side agent setting or custom environment may still store secrets in the control plane, so the UI must state where each secret lives and which run receives it. [Multica runtime data boundaries](https://multica.ai/docs/daemon-runtimes).
- Maintain a recurring upstream-sync process: review stable Paperclip releases, security fixes, changed schemas and design tokens; merge into a staging branch; run compatibility and visual checks; document conflicts and release a pinned Crewspan version.

## 5. Delivery sequence and release proof

All milestones are required for the first public release; they are sequenced to keep the fork reviewable.

1. **Fork and baseline.** Pin upstream, build it unchanged, record UI screenshots and tests, map inherited APIs and data, create the compatibility matrix and threat model. Specifically inventory Paperclip's adapter, execution environment, skill, routine, notification and chat facilities before designing new records. Record which Multica behaviours are product references and which are excluded by the source/licence boundary. Exit when a clean Paperclip organisation runs on the intended VPS configuration.
2. **Identity and scoped access.** Add hybrid org nodes, human leadership, allocation, central authorisation, project/file/agent/runtime grants and migration. Ship effective-access explanations and access requests with this milestone, so operators can understand denied actions. Exit when unauthorised users and agents are denied through UI, API, search, events and downloads.
3. **Projects and isolated execution.** Add project Files, permission-aware retrieval, safe artifacts, capability-checked Direct/Parallel modes and mandatory contained runners. Establish company-owned VPS pool first; enable remote/personal runners only after registration, consent, offline recovery and equivalent isolation are proven. Exit when two simultaneous projects can run agents and cross-project filesystem/API/credential reads fail.
4. **Delegation and model governance.** Add lane configuration, explicit Assign/Start operations, mixed-lead delivery teams, task-backed child runs, review outcomes, Connections-based model policy, approved fallback and complete cost attribution. Exit when a cheaper delegate can be compared against direct execution using **cost per accepted task**, including rework.
5. **Communication, Inbox and repeatable methods.** Add DMs, channels, mention-trigger previews, threads and deduplicated notifications; connect them to tasks and runs. Extend existing Paperclip skills/routines with versioning, runbooks and guarded schedules/webhooks. The approved skill-improvement proposal loop can follow this milestone without delaying the core journey. Exit when a human can request an agent in a channel, see progress, review the artifact and receive the decision in one coherent flow.
6. **Release hardening.** Run full Paperclip regression coverage, Crewspan permission and isolation tests, migrations both ways where possible, backup/restore, load and accessibility checks, visual comparison and a fresh-VPS installation. Publish documentation, security model, limitations, upgrade guide and a reproducible demo organisation.

**Non-negotiable test scenarios:** human CEO and agent CEO; human-led and agent-led delivery teams; assignment without starting; mention-trigger preview; mixed reporting without cycles; scoped manager delegation; denied project and agent selectors; restricted file search and download; revoked access during an active run; forbidden model fallback; expired credential; duplicate message/run delivery; concurrent worktrees; fail-closed worktree capability downgrade; unreproducible local input snapshot; company runner offline/reconnect and duplicate claim; interrupted delegation and retry; reviewer requests changes; inbox deduplication; skill version pinning and restricted-source rejection; webhook deduplication and repeated-failure pause; restore from backup; and a user completing the complete journey on desktop and narrow browser layouts. Before enabling personal runners, additionally prove owner consent, revocation, offline handling and isolation parity.

### Release proof beyond the feature checklist

- Run a three-person, three-agent, two-project pilot: a human CEO leads one team, an AI CEO or lead routes another, one project is repository-backed and one contains only documents. Demonstrate a request for access, a scoped approval, a channel mention, a child delegate, independent review, a published artifact, cost attribution and a denied cross-project read.
- Compare direct and delegated paths for the same representative tasks using total provider usage, wall time, review/rework and accepted-result quality. Keep delegation optional if it does not improve the measured outcome for that lane.
- Drill a disconnected runner, a cancelled run, a revoked grant during execution, a revoked personal-runtime share, a failed worktree setup and a restore from backup. All must leave a comprehensible run state and no secret or cross-project data leak.
- Review every new screen beside its nearest Paperclip ancestor. The release candidate must satisfy both task completion and visual continuity; no imported Multica UI is part of the implementation.

### Deferred choices, stated explicitly

- A browser-first Paperclip client ships first. Multica's desktop and iOS clients demonstrate a possible later distribution path, but do not justify a native rewrite or a desktop-only dependency for Crewspan.
- Company-owned VPS runners are the first supported execution location. Remote/personal runners are valuable for local files or existing tool subscriptions, but require the consent, capability and isolation gates above before general release.
- AI-assisted agent setup may draft instructions, skills and model choices, as Multica's agent builder does, but a human must review the effective access, runtime and spend envelope before activation. [Multica agent setup](https://multica.ai/docs/agents-create).
- The skill-improvement loop is opt-in and human approved. It follows a reliable task/review/skill-version foundation rather than becoming an automatic prompt rewrite mechanism.

**Assumptions locked for this plan:** Crewspan is an open public fork prioritising self-hosting, not a paid hosted service; any knowledge-work team can create projects without code repositories; the initial client follows Paperclip’s browser app; provider accounts and subscriptions follow Paperclip’s existing Connections model; DMs and channels are required at first public release; and the visual language remains Paperclip’s.
