# Crewspan — M0 outcome and M1 handoff

**Audience:** whoever builds Crewspan next — human or agent, including a fresh clone in a cloud sandbox.
**Status:** M0 closed with a recorded **Go with changes**. M1 is authorised. **M1's first priority is a Windows desktop release with auto-update.**

## 1. What Crewspan is

Crewspan is a fork of Paperclip — upstream `github.com/paperclipai/paperclip`, fork `github.com/sico-vibes/crewspan`, default branch `main`. Upstream is **MIT**, so rebranding and unrestricted development are permitted. It is a control plane for teams of AI agents: people and agents work inside one company/org, with governance over what agents may see, use, and spend.

- Product intent: `docs/CREWSPAN-PRODUCT-CONTRACT.md`
- Plan and milestones: `doc/plans/2026-09-24-crewspan-e2e-v3.md`
- Delivery architecture decision: `doc/decisions/ADR-0001-desktop-and-web-delivery.md`

## 2. How the code runs

- pnpm monorepo, Node ≥ 24.11: `server/` (Node/TS), `ui/` (React 19 + Vite SPA), `cli/`, `packages/*` (adapters, db, plugins, and a Rust runner).
- Local reference instance: `C:\Crewspan`, `PAPERCLIP_HOME=%USERPROFILE%\.paperclip`, instance `default`, listener `127.0.0.1:3100`.
- Windows launcher: `Start-Default.ps1 [-Mode dev|production]` — **`dev` is the default** so ordinary starts keep working; production is opt-in.
- The shipped container's own start command is the production reference:
  `node --import ./server/node_modules/tsx/dist/loader.mjs server/dist/index.js`
  Raw `node dist/index.js` **cannot** work in a workspace-linked checkout, because `@paperclipai/db` exports `./src/*.ts`.

### Windows build gotchas already fixed — do not regress
- Cross-platform asset copying in `packages/db` and `server` build scripts (no Unix `cp`/`mkdir -p`).
- `pathToFileURL()` before dynamic `import()` in the Storybook scripts.
- CRLF→LF normalisation in generated checks, so a Windows checkout cannot fake stale output.
- Workspace links must be **junctions**, not symlinks, when Windows Developer Mode is off (`EPERM` otherwise).

## 3. M0 outcome — why "Go with changes" and not a clean Go

The gate is §3.5 of the v3 plan, with exit criteria in §14.

- Recommendation: `doc/plans/2026-09-30-m0-go-no-go-recommendation.md`
- Decision packet: `doc/plans/2026-09-30-m0-board-decision-packet.md`
- Spike evidence: `doc/plans/2026-09-29-crewspan-m0-spike-evidence.md`
- Baseline/UI/threat-model evidence: `UPSTREAM.md`, `doc/design/M0-UI-BASELINE.md`, `doc/M0-TERM-TABLE.md`, `doc/M0-THREAT-MODEL.md`, `doc/M0-TRADEMARK-SCREEN.md`, `doc/M0-EXPLICIT-UNKNOWNS.md`

**Why the spikes could not be verified at this stage — three independent reasons:**

1. **S3 (containment) failed.** No API-key-capable adapter was proven to run contained, and the §9.14 fail-closed suite never ran: the shipped image carries no `bwrap`, `podman`/`runsc` are absent on the host, and no provider key was supplied. This is **absence of evidence, not evidence of an escape.**
2. **The remaining spikes need production integration.** S1 (scoped-access route/query integration + leak tests), S2 (upstream sync rehearsal), S4 (production broker and the 1 GB/30 s gate), S5 (a real adapter/gateway run), S6 (provider-session integration) and S7 (company-setting storage) all require building the feature. A **feasibility** gate cannot be satisfied by constructing the product, so those pass conditions are unreachable inside M0.
3. **The gate's two quantitative inputs are unmeasured.** A Go needs the M2 retrofit estimate **≤18 engineer-weeks** and the upstream sync cost **<2 engineer-days**. Neither has been measured, and §14 additionally requires M1–M7 re-baselined — not done. A gate that cannot be evaluated is not a clean Go.

**Decision (Board, 2026-09-30): "Go with changes."** S1–S7 are re-scoped into M1 exit criteria. **S3 becomes an M1 gate: containment must be proven before any agent runs against real data.** M1 may start.

## 4. M1 — first priority: the desktop release

**Goal:** an installable, self-updating **Windows desktop app** for Crewspan, published as a beta release from this repository.

1. **Tauri shell** that launches the *built* server as a loopback sidecar with an embedded database, waits for health, loads the SPA, and stops the sidecar on quit. Tauri over Electron: this repo already contains Rust, and the result is far smaller and faster.
2. **Windows beta installer published as a GitHub Release** from this repo — installable on a clean machine with no dev toolchain and no external PostgreSQL.
3. **Auto-update from GitHub Releases**, so publishing a release updates an installed app with no manual reinstall. No OS code signing for now — Tauri's updater uses its own generated key pair.
4. **No refactor:** keep the server + SPA monolith; one API client with a configurable base URL.
5. **Native packaging per OS** (runner + sandboxing) is the long pole, not the app code.

**Definition of done for this first milestone:** a Windows user installs the beta from Releases, it runs, and the next published release auto-updates it.

## 5. Carried into M1 (former M0 exit criteria, now re-scoped)

- Prove **S3** containment (fail-closed) and run the §9.14 probe suite.
- Measure and record the **M2 retrofit sizing** and the **upstream sync cost**.
- Complete **S1/S2/S4–S7** as M1 exit criteria.
- Bring the reference instance to **`authenticated`** mode.
- DR hardening: startup backup, retention alignment (7 daily + 4 weekly), independent key escrow, and boot the restored database at least once.

## 6. Open Board decisions — do not decide these in code

**B1** telemetry · **B2** announcements feed · **B3** npm/update channel and CLI scope · **B4** brand implementation depth · **B5** Paperclip Cloud · **B6** auth route/hostname/exposure/bootstrap · **B7** backup retention, key escrow and DR set · **B8** migration vs fresh · **B9** baseline re-pin.

## 7. Constraints that must not be broken

- Port **3100 stays loopback-only** — never expose it.
- Never commit credentials, tokens, or `PAPERCLIP_AGENT_JWT_SECRET`; never print the instance env file.
- The reference instance and the VPS belong to the operator; agents work in worktrees. Deploy, restart, migration, restore, and any destructive action need explicit authorisation.
- **Do not vendor Multica code.** Its Apache-2.0 conditions (attribution, branding, no third-party hosting) travel with the code, and it would not integrate with this TypeScript stack anyway. Reimplement patterns.
